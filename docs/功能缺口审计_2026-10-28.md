# 拾光手办 · 功能缺口与缺陷审计

> 审计日期：2026-10-28  
> 审计范围：`miniprogram/`（26 页面 / 7 组件 / 10 个 utils）、`cloudfunctions/`（11 个云函数）、`config/`  
> 当前形态：纯展示（`DEMO_MODE = true`、`MODULE_SWITCH.trade = false`、tabBar 3 项）  
> 审计方法：静态代码核查 + 自检脚本 + mock 链路实测（Node 直调 `mock.handle`）



---

## 一、总体结论

工程结构是完整的：26 个页面四件套齐全、11 个云函数全部登记、`check-wxml` / `check-api` / `check-modules` 三项自检全部通过、tabBar 图标与页面跳转无死链。

**但「结构完整」与「功能可用」之间存在明显落差**，集中在两点：一是纯展示形态下依赖 `DEMO_MODE` 的 mock 数据，而 mock 对收藏与后台鉴权是**空转实现**，导致用户能碰到的两个功能实际不生效；二是作品数据只填了文字描述，详情页设计出的规格、尺寸、对照、环视四个区块全部无数据。

按「用户是否真的会碰到」排序，问题分四层：

| 层级 | 性质              | 数量  | 是否需要立刻处理 |
| -- | --------------- | --- | -------- |
| A  | 当前形态下用户可触达的功能缺陷 | 2   | 是，上线前必修  |
| B  | 内容空缺，页面区块空白     | 4   | 是，影响转化   |
| C  | 已完整实现但未启用（交易模块） | 1 组 | 否，形态决定   |
| D  | 代码就绪、缺外部配置      | 7 项 | 上线前按需配置  |

## 二、A 层：当前形态下就能碰到的功能缺陷

### A1. 收藏功能全链路失效

`favorite` 的三个 action 在 mock 里都是固定返回值，不读写任何存储：

| action   | 实现                                  | 位置                   |
| -------- | ----------------------------------- | -------------------- |
| `check`  | 恒返回 `{ favorited: false }`          | `config/mock.js:667` |
| `toggle` | 恒返回 `{ favorited: true, count: 3 }` | `config/mock.js:668` |
| `list`   | 恒返回 `PRODUCTS.slice(0, 2)`          | `config/mock.js:665` |

实测（Node 直调 mock）：

```
1) 初始 check   : {"favorited":false}
2) 点击 toggle  : {"favorited":true,"count":3}
3) 再 check     : {"favorited":false}      ← 状态丢失
4) 收藏列表     : 2 件 → 蓝发少年、敖丙     ← 与用户操作无关
5) 取消后 list  : 2 件                      ← 列表不变
```

**用户看到的现象**：详情页点收藏 → 提示「已收藏」、心形变实心；退出重进 → 变回空心；进收藏页 → 永远是「蓝发少年、敖丙」两件；在收藏页点取消 → 列表纹丝不动。

**根因**：收藏被当成需要后端的能力，但纯展示形态下作品数据是静态的 `config/works.js`，收藏完全可以在本地完成。项目里已有同类先例——`utils/history.js` 用 `wx.setStorageSync` 实现浏览历史，工作正常。

**建议**：新增 `utils/favorite.js`（照 `history.js` 的模式，存 `_id` 数组 + 存作品快照），把 `detail.js:184` 的状态查询、`detail.js:271` 的切换、`favorite.js` 的列表与取消全部改走本地。云函数 `favorite` 保留给交易模式，用 `DEMO_MODE` 分流。工作量约 1 小时，是当前形态下性价比最高的修复。

### A2. 管理后台入口对所有用户开放，且口令校验形同虚设

| 环节    | 现状                                 | 位置                       |
| ----- | ---------------------------------- | ------------------------ |
| 是否管理员 | mock 的 `login` 恒返回 `isAdmin: true` | `config/mock.js:484`     |
| 口令校验  | mock 的 `checkAuth` 直接发令牌，不比对口令     | `config/mock.js:674-676` |

实测：`checkAuth({ password: '随便乱输' })` → `{ code: 0, data: { token: 'demo-token' } }`，验证通过。

**用户看到的现象**：任意用户进「我的」→ 底部出现「管理后台」→ 输入任意字符 → 直接进入 dashboard 看到演示数据。

**风险评级**：演示模式下后台数据来自 mock，改不了真实内容，所以不是数据安全事故；但它是**不该出现的入口**，用户点到会困惑，审核也可能被质疑「展示类小程序为何有商家后台」。

**建议**：mock 的 `isAdmin` 改为 `false`，演示模式不暴露后台入口（该模式下后台改数据本就不落库，没有预览价值）。若确需在开发者工具里看后台 UI，直接用编译模式指定 `pages/admin/dashboard/dashboard` 即可。

## 三、B 层：内容空缺，页面区块空白

详情页按设计有 8 个内容区块，实际有 4 个永远不渲染，因为作品数据里对应字段全空：

| 区块            | 依赖字段                | 填充率      | 后果                                            |
| ------------- | ------------------- | -------- | --------------------------------------------- |
| 作品描述          | `detail[]`          | 27/27    | 正常                                            |
| 规格表（材质/尺寸/工序） | `specs[]`           | **0/27** | 区块隐藏                                          |
| 尺寸对照（与实物比）    | `dimension`         | **0/27** | 区块隐藏                                          |
| 竞品对照表         | `compare`           | **0/27** | 区块隐藏                                          |
| 360° 环视       | `panorama.frames[]` | **0/27** | `hasPanorama` 恒 false，入口永不出现（`detail.js:119`） |

### B1. 三条业务线只有一条有内容

需求定义的三条线是「现货 / 限量预售 / 定制预约」，当前 27 件作品：

- `type` 全为 `0`（现货），**限量预售 0 件**
- `limitNum` 全为 `0`，**限量编号功能无任何数据可展示**
- 定制预约靠客服会话承接，已实现

也就是说「限量预售」在代码里完整存在（`PRODUCT_TYPE.PRESALE`、`isPresale`、编号强绑定逻辑都在），但**没有任何一件作品属于这一类**，相关 UI 分支永远不会走到。

### B2. 详情图密度过低

| 规格                  | 数量   | 说明                       |
| ------------------- | ---- | ------------------------ |
| 缩略图（主包 480px WebP）  | 27 张 | 每件 1 张，齐全                |
| 详情图（分包 1000px WebP） | 34 张 | 27 件里 21 件只有 1 张，6 件 2 张 |

原图有 130 张，受分包 2MB 限制只能放 34 张。这是硬约束下的取舍，不算缺陷，但**详情页的可看性明显吃亏**——用户点进详情，看到的图和列表页一样。要放更多图只有两条路：降规格（`--detail 900 --detail-q 74` 可多放约 6 张）或上云存储。

### B3. 编号查询无真实登记

`verify` 页的两级校验设计是对的：本地校验格式（`SG + 年份 + 四位序号`，末位是校验位），云端查 `verifyCodes` 集合。

但当前 `verifyCodes` 未录入任何真实编号，mock 里只认一个演示码 `SG20260128`（`mock.js:527-544`）。**用户手里任何真实作品都查不到**。

### B4. 详情页「作品说明」标题下的版权/交易提示

`detail.wxml:66` 价格区在 `price <= 0` 时显示「询价」（逻辑正确，27 件全走 this 分支），这部分没有问题。此处仅作记录：全形态下不会出现 `¥0.00`。

## 六、安全隐患

### S1. `ADMIN_SECRET` 有硬编码默认值

| 位置                                 | 代码                                                                         |
| ---------------------------------- | -------------------------------------------------------------------------- |
| `cloudfunctions/admin/index.js:16` | `const SECRET = process.env.ADMIN_SECRET \|\| 'fd-admin-secret-change-me'` |
| `cloudfunctions/stats/index.js`    | 同上                                                                         |

**实际风险等级：中**。令牌签发发生在 `ADMIN_PASSWORD` 校验通过之后（`admin/index.js:94-99` 未配密码时直接返回 500，不会放行），所以攻击者仍需先知道口令。真正的问题是**口令一旦泄露，无法通过轮换 SECRET 止损**——SECRET 仍是公开的默认值。

**建议**：改为无默认值，未配置时直接拒绝签发令牌并给出明确报错。这与 `ADMIN_PASSWORD` 的处理方式一致。
